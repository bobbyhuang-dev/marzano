# Contributing to Marzano

Thanks for taking an interest. Marzano is a small, one-person project, so the
process is light: open an issue for anything bigger than a typo, keep pull
requests to one change each, and expect a reply within a few days rather than
hours.

## Before you start

- **Bugs:** open an issue with the browser and OS, the steps to reproduce, and
  what you expected instead. Marzano keeps everything in the browser, so please
  do not attach a backup file that holds your real tasks.
- **Features and behaviour changes:** open an issue first and say what problem
  it solves. The app is deliberately small (a task list, a calendar, tags, a
  Pomodoro timer, and nothing that needs a server), and a change that needs an
  account, a backend, or a network call is out of scope.
- **Small fixes** (copy, a11y, a clear bug with a clear fix) can go straight to
  a pull request.

## Setting up

Marzano needs **Node 24 LTS** (pinned in `.nvmrc`; 20.19+ and 22.13+ also work)
and **pnpm** (pinned through `packageManager`, so `corepack enable` is enough).
npm or yarn will write a lockfile the project does not track.

```bash
nvm use            # or: fnm use
corepack enable
pnpm install
pnpm dev           # Vite dev server
```

## Checking your change

There is no test suite. The build is the gate, and the deploy workflow runs the
same two commands on every push to `main`:

```bash
pnpm lint          # eslint .
pnpm build         # tsc -b (type-check) then vite build -> dist/client/
```

Both must pass before a pull request is ready. If you changed the brand mark in
`src/lib/brand.ts`, run `pnpm icons` and commit the re-rendered files in
`public/` as well; the deploy has no render step.

## How the code is laid out

`CLAUDE.md` is the architecture guide and is worth reading before a change of
any size. The rules that most often catch people:

- **`src/lib/` holds the logic; components stay presentational.** Each module
  owns one slice of persisted state and its own `load*` / `save*`.
- **Extend the validator when you add a field.** Every record is read back
  through a tolerant `toX()` function. A field it does not read is silently
  lost on the next load.
- **Never spread a change into a task or tag.** Use `touchTask` / `touchTag`
  so the `updatedAt` stamp moves, and delete with `tombstone()` rather than a
  `filter`, or the JSON merge will put the record back.
- **Never call `new Date(task.dueAt)`.** A due date is either a day or an
  instant; go through the helpers in `lib/tasks.ts`.
- **Style from the tokens, never from a raw colour.** Light and dark are HSL
  triples in `src/index.css`; shadows and overlays are tokens too. Motion is
  `transition-ui` or the presets in `lib/motion.ts`, not a hand-written
  transition.
- **Every mutation announces itself** through `setStatusMessage`, so screen
  readers hear it.
- `src/components/ui/` is generated by shadcn/ui. Regenerate rather than
  hand-edit where practical (`duration-picker.tsx` is the documented
  exception).
- Files are kebab-case, components use named exports, and comments explain
  *why* a decision was made, not what the code does.

## Commit messages are the release notes

Marzano's changelog ("What's new" in the sidebar) is built from the git log at
build time. Write commits for a reader of the app, not the repository:

- Use [Conventional Commits](https://www.conventionalcommits.org):
  `type(scope): imperative subject`, subject under 72 characters.
- `feat` and `fix` (and any other type not listed below) appear in the
  changelog. The subject, minus its `type(scope):` prefix, is the headline;
  the body paragraphs are the notes.
- `chore`, `ci`, `build`, `docs`, `refactor`, `style`, `test` and `revert` are
  hidden. A deploy made only of those announces nothing.
- The body says why the change was needed, not what the diff already shows.

## Pull requests

- Branch from `main`. One change per pull request.
- Describe the user-visible behaviour and include a screenshot or recording
  for anything visual, in light and dark if the change touches colour.
- Squash to commits that each read as a release note (see above).
- A merge to `main` deploys to production straight away, so a merged pull
  request is a release.

## Security

Please do not report security issues in a public issue. See
